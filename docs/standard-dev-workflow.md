# 软件开发标准流程（dialux-compiler 版）

> 场景：dialux-compiler 项目开发 | 用途：从需求到干净交付的完整链路 | 版本：v1（2026-09-07）
> 来源：AGENTS.md 开发流程 + 标准任务流程 v1（六步链）合并固化为本项目可执行版
> 约束：本文件是「流程」，不是「状态」；进度/数字/验收一律以 `KANBAN.md` 为准

## 一句话

把一条开发需求从「模糊想法」推进到「门禁全绿 + 真机验证 + 文档对齐 + 干净提交」的七步链：
**素材 → 定案 → 计划 → 执行 → 门禁 → 真机 → 收尾提交**。

## 七步链

| 步骤 | 动作 | 触发条件 | 产出物 |
|---|---|---|---|
| ① 素材/现状 | 读输入（截图/资料/附件/旧代码），跑 `git status` 看工作区有没有别人的未提交改动 | 每次拿到新任务先看清现状 | 内容要点 + 现状确认 |
| ② grill（batch-grill-me） | 批量拷问：把设计树前沿问题一次抛完，每条带推荐答案，用户确认或改 | 有任务/功能需要定案（口径、边界、取舍） | 决策表（问题 + 定案） |
| ③ plan | 把定案落成执行计划文档（步骤/文件/风险/验证） | 决策已定 | 计划文档（如 `docs/plan-*.md`） |
| ④ 执行 | 按 karpathy-guidelines 执行（surgical、简洁、目标驱动） | 计划在手 | 代码/测试/文档 |
| ⑤ 门禁 | `python -m pytest tests/ -q` + `python -m ruff check .` 全绿；数字以 KANBAN「门禁实测」为准 | 代码写完 | 门禁数字（如 231 passed + ruff 0） |
| ⑥ 真机验证 | 真实图纸 / DIALux 真机跑一遍，按 AC rubric 打分（AC 编号定义见 KANBAN「需求 ID 溯源」） | 影响运行态的改动 | 验证证据（日志/拆包/截图） |
| ⑦ 收尾 | neat-freak 对账（文档/规则/工作区对齐）+ git 语义提交（分组 commit） | 门禁+真机通过 | 无残留、文档同步、干净提交 |

## 关键规则

1. **先看工作区**：动代码前 `git status`；有别人未提交改动 → 停下问架构师，不在半成品上叠改
   （起因 2026-09-03 文档并发改写事故）
2. **grill 带建议**：每个前沿问题都给推荐答案，不是干问
3. **spec 先行**：写 spec（输入/输出/验收）或口头给目标，再动手
4. **门禁是硬门槛**：不得靠改 ruff 配置或注释掉测试把门禁做绿；数字绑定 ruff 版本与 .gitignore 忽略面
5. **真机说话**：影响 DIALux 的改动必须真机验证，不拿「应该能行」当证据
6. **提交分组**：按语义分组 commit（feat/docs/fix），每个提交一件事；LF/CRLF 警告无害
7. **收尾必做**：neat-freak 对账 + 删除候选需用户确认；记忆写入需授权

## 调用示例

- 用户说「继续开发」「按流程走」→ 从 ② 或 ④ 进入（现状清楚则直接执行）
- 用户丢来新截图/资料 → 先走 ①，读懂确认用途再进 ②
- 用户说「收尾」「洁癖」→ 走 ⑦ neat-freak

## 与 AGENTS.md 的关系

- `AGENTS.md` = 规则层（铁律、工具分工、MVP 路线），是**约束**不是流程
- 本文件 = 流程层（每一步做什么、产出什么），是**执行指引**
- 状态/数字/验收唯一现役在 `KANBAN.md`，本文件不复述
